1. System Overview Overview

The entire messaging system has two entry points (Campaign and Automation) that both funnel into a single shared delivery pipeline. The delivery pipeline is medium-agnostic — it dispatches to the correct provider adapter based on channel. Every send is tracked, every interaction feeds back into analytics, and every conversion is attributed.

Campaign vs Automation — Side by Side

Campaign (One-Off Broadcast)

TriggerAdmin clicks "Send" in UI
AudienceExplicit segment selection at creation time
TimingImmediate or scheduled (single moment)
Content1-N variants (A/B test), same for all recipients
ChannelsSingle medium per campaign (email, SMS, or WA)
LifecycleDraft → Scheduled → Sending → Sent → Analyzing
StateStateless per recipient — send once, track outcome
GoalOptional (e.g., purchase within 7 days). Measured, not enforced.
AnalyticsCampaign-level funnel, variant comparison, heatmaps

Automation (Event-Triggered Flow)

TriggerSystem event (user.registered, order.completed, segment.entered, etc.)
AudienceImplicit — whoever triggers the event
TimingContinuous — runs whenever trigger fires
ContentPer-step templates, personalized per user context
ChannelsMixed mediums within one flow (email step, then SMS step, etc.)
LifecycleDraft → Active → Paused (always running while active)
StateStateful per enrollment — tracks which step each user is on
GoalEnforced — user exits flow early when goal is met
AnalyticsPer-step funnels, drop-off rates, time-to-goal, revenue per flow
Key Architectural Insight

Both campaigns and automations converge into the same delivery pipeline at the "Guardrails Gate" step. From that point forward, the system doesn't care whether a message originated from an admin clicking "Send" or from a user.registered event firing. The delivery pipeline handles consent checking, recipient filtering, template rendering, link rewriting, provider dispatch, logging, and webhook processing identically.

This means: build the delivery pipeline once, both entry points use it.

The Internal "Send Request" — Universal Payload

Regardless of whether a campaign or automation initiated the message, the delivery pipeline works with a single internal data structure. This is the payload that flows from the entry point into the shared pipeline:

INTERNAL: DeliveryRequest (what enters the shared pipeline) ▼
{ // === WHO === "user_id": "uuid", "to_email": "user@example.com", // resolved from core.users "to_phone": "+15551234567", // resolved from core.users (nullable) "to_whatsapp": "+15551234567", // resolved from core.users (nullable) // === WHAT === "channel": "email", // "email" | "sms" | "whatsapp" "template_id": "welcome_series_1", // DB template name "template_data": { // per-user merge variables "first_name": "Alice", "product_name": "Premium Plan", "unsubscribe_url": "https://..." }, "subject": "Welcome to MyApp!", // email only (from template or override) "html_content": null, // pre-rendered HTML (if skipping template) // === WHERE FROM === "source_type": "campaign", // "campaign" | "automation" "campaign_id": "uuid", // which campaign (always set) "variant_label": "A", // A/B variant (campaign only) "flow_id": "uuid | null", // which flow (automation only) "flow_step_id": "uuid | null", // which step (automation only) "enrollment_id": "uuid | null", // which enrollment (automation only) // === TRACKING === "utm_source": "myapp", "utm_medium": "email", // "email" | "sms" | "whatsapp" "utm_campaign": "welcome_series", "utm_content": "variant_a", // === GUARDRAILS (pre-computed) === "bypass_frequency_cap": false, // true for critical transactional "bypass_quiet_hours": false, "message_type": "marketing" // "transactional" | "marketing" }
Why This Matters

This universal DeliveryRequest is the contract between entry points and the pipeline. A campaign resolves its audience segment into N of these requests (one per recipient). An automation flow's "send" step creates exactly one. The pipeline doesn't need to know which path generated it.

1
API Call — Admin Triggers Send

Admin clicks "Send" in the campaign wizard UI. Frontend calls the campaign send endpoint.

Audience Resolution

The delivery service calls segment_service.compute_segment_users(segment_ids) to resolve who should receive the campaign. This runs the segment's filter rules against the database.

INTERNAL: Segment Resolution Query ▼
-- segment_service builds this SQL dynamically from segment filters: SELECT DISTINCT u.id, u.email, u.phone, u.whatsapp_number, u.first_name FROM core.users u LEFT JOIN ecommerce.customer_metrics cm ON cm.user_id = u.id WHERE u.email_verified = true AND u.id NOT IN (SELECT user_id FROM gdpr.email_preferences WHERE suppressed_at IS NOT NULL) -- Segment filter: "purchased in last 30 days" AND cm.last_order_at >= NOW() - INTERVAL '30 days' -- Segment filter: "RFM segment = champion or loyal" AND cm.rfm_segment IN ('champion', 'loyal') -- Result: list of user records -- e.g., 2,847 users match this segment

3
Recipient Filtering

Each resolved user is checked against multiple exclusion criteria. Users who fail any check are skipped and logged as "excluded" with a reason.

INTERNAL: Filter Pipeline (per user) ▼
Filter Pipeline (each user passes through ALL checks): 1. CHANNEL AVAILABILITY - If medium=email: does user have email? (always yes, required field) - If medium=sms: does user have phone? Bob has no phone → SKIP (reason: "no_phone") - If medium=whatsapp: does user have whatsapp_number? → SKIP if missing 2. SUPPRESSION CHECK - Query gdpr.email_preferences WHERE user_id = :uid AND suppressed_at IS NOT NULL - If suppressed → SKIP (reason: "suppressed") 3. CONSENT CHECK - If message_type = "marketing": - Email: check gdpr.email_preferences.marketing_email = true - SMS: check marketing.user_communication_preferences has sms consent - WA: check marketing.user_communication_preferences has whatsapp consent - If no consent → SKIP (reason: "no_consent") 4. ALREADY RECEIVED CHECK - Query campaign_recipients WHERE campaign_id = :cid AND user_id = :uid - If already sent → SKIP (reason: "already_sent") - Prevents duplicates on retry/resume 5. SUNSET POLICY CHECK - If user hasn't opened any message in N days (configurable) → SKIP (reason: "sunset") Result for 2,847 resolved users: - 2,412 pass all filters → eligible to receive - 187 skipped: no_phone (SMS campaign) - 143 skipped: no_consent - 89 skipped: sunset - 16 skipped: suppressed
4
Guardrails Check (per recipient)

Each eligible recipient is checked against frequency caps and quiet hours. Users over their cap are deferred or skipped. Users in quiet hours are delayed.

INTERNAL: Guardrails Check ▼
For each eligible recipient: 1. FREQUENCY CAP - Query message_pressure_log: SELECT COUNT(*) FROM marketing.message_pressure_log WHERE user_id = :uid AND channel = :ch AND sent_at >= NOW() - INTERVAL '7 days' - Config: max 3 marketing emails per 7 days - If count >= 3 → DEFER or SKIP (reason: "frequency_cap") 2. QUIET HOURS - Resolve user's timezone (from profile or geo) - Config: no marketing messages between 21:00-08:00 local time - If within quiet hours → DEFER to 08:00 next day - Deferred sends get scheduled_at set, not skipped 3. PER-CHANNEL DAILY CAP - Config: max 1 SMS per day per user - If already sent SMS today → SKIP Result for 2,412 eligible users: - 2,298 clear all guardrails → proceed to send - 87 deferred: quiet hours (will send at 08:00 their time) - 27 skipped: frequency_cap
5
Variant Assignment + Template Rendering

Recipients are assigned to A/B variants by weight, then templates are rendered with per-user merge variables.

INTERNAL: Variant Assignment + Render ▼
A/B Variant Assignment: Campaign has 2 variants: Variant A: weight=60, subject="Welcome back, {{first_name}}!" Variant B: weight=40, subject="We miss you, {{first_name}}!" Load template from marketing.email_templates WHERE name = 'winback_v2' 2. Jinja2 render: html_content with template_data merged 3. Result: fully rendered HTML string per user Output: rendered_html = "<html>...Hello Alice, here's 20% off...</html>" subject = "Welcome back, Alice!"

-- F10: Provider stats pull to backfill missed webhooks For each campaign sent in the last 7 days: IF provider.supports_campaign_stats: provider_stats = await provider.get_campaign_stats(campaign.provider_campaign_id) our_stats = SELECT * FROM campaign_stats_summary WHERE campaign_id = :cid delta = { "delivered": provider_stats.delivered - our_stats.total_delivered, "opened": provider_stats.opened - our_stats.total_opened, "bounced": provider_stats.bounced - our_stats.total_bounced } IF any delta > threshold (e.g., > 5%): LOG warning: "Campaign {id}: provider reports {X} delivered vs our {Y}" UPDATE campaigns SET last_reconciled_at = NOW(), reconciliation_delta = :delta_json -- Note: We can't backfill individual recipient records from provider stats. -- We can only detect aggregate discrepancies and flag them for investigation. -- The real fix is webhook reliability (retry, idempotency).
Campaign Flow Summary

Admin action → Resolve audience → Filter (suppress/consent/sunset) → Guardrails (freq cap/quiet hours) → Assign variant → Render template → Rewrite links → INSERT-BEFORE-SEND → Provider dispatch → UPDATE status → Webhooks update delivery/open/click → Background workers aggregate stats → Dashboard shows funnel.

The provider's only role: deliver the message and fire webhooks. Everything else is ours.

Timeout, Completion, and Flow Chaining

Users exit a flow in one of four ways. If the flow has an exit tag and another flow is triggered by that tag, flow chaining occurs.

INTERNAL: Exit Paths + Flow Chaining ▼
Four Exit Paths: 1. COMPLETED — user reached the last step (next_step_id = null) → status = 'completed', completed_at = NOW() 2. TIMED_OUT — enrolled_at + timeout_days < NOW() → status = 'timed_out', completed_at = NOW() → Checked by Flow Worker every 60s 4. Medium Selection Matters

Campaigns are single-medium — one campaign = one channel. You can't send the same campaign as both email and SMS. To reach users on multiple channels, create separate campaigns per channel (targeting users who have that channel available).

Automation flows are multi-medium — step 1 can be email, step 2 can be SMS, step 3 can be WhatsApp. This is the power of flows: you can escalate across channels within a single sequence.

Multi-Touch Attribution (Computed at Report Time)

A user might interact with multiple campaigns before converting. The 5 attribution models distribute credit differently. These are computed when an admin views the report, not at conversion time.

ATTRIBUTION: 5 Models Explained ▼
Example: Alice interacted with 3 campaigns before purchasing ($100): Touch 1: Email campaign "Spring Sale" (April 18) — opened, no click Touch 2: SMS campaign "Flash Deal" (April 22) — clicked Touch 3: Email campaign "Winback Q4" (April 25) — clicked → purchased Attribution Models (computed at report time): 1. LAST-CLICK (default) "Which campaign directly preceded the conversion?" → Winback Q4 gets 100% credit ($100) → Most common, simplest, but ignores awareness campaigns 2. FIRST-TOUCH "Which campaign first brought the user into the funnel?" → Spring Sale gets 100% credit ($100) → Good for measuring top-of-funnel effectiveness 3. LINEAR "Distribute credit equally across all touchpoints" → Spring Sale: 33.3% ($33.33) → Flash Deal: 33.3% ($33.33) → Winback Q4: 33.3% ($33.34) → Fair but dilutes signal 4. TIME-DECAY "Recent touches get more credit (exponential decay)" → Spring Sale: 10% ($10.00) — 7 days ago → Flash Deal: 30% ($30.00) — 3 days ago → Winback Q4: 60% ($60.00) — same day → Formula: weight = 2^(-days_ago / half_life), half_life = 7 days 5. U-SHAPED (Position-Based) "First and last touch get 40% each, middle touches split 20%" → Spring Sale: 40% ($40.00) — first touch → Flash Deal: 20% ($20.00) — middle touch → Winback Q4: 40% ($40.00) — last touch (conversion) → Good balance of awareness + conversion credit // These are NOT stored as separate records — the touch_sequence JSON // on campaign_attributions contains all touches. The attribution model // is applied at query time via SQL window functions. // Admin chooses which model to view in the dashboard. // "Switch model" just changes the SQL aggregation, not the data.

The Attribution Window

How the Attribution Window Works

Each campaign has an attribution_window_days setting (default: 7 days). A conversion is only attributed to a campaign if it happens within this window after the user's last interaction (click) with the campaign.

Example: Campaign sent April 25, attribution_window = 7 days. If Alice clicks on April 25 and purchases on April 30 → attributed. If she purchases on May 5 → NOT attributed (outside 7-day window).

The window is per-campaign. A user can be within the attribution window of multiple campaigns simultaneously — that's exactly when multi-touch attribution models matter.

CONSENT: How Consent Is Checked Per Channel ▼

Guardrail 2: Suppression Check

SUPPRESSION: Hard Block on All Messages ▼
Suppression is a HARD BLOCK — overrides all consent. A suppressed user receives ZERO messages of any type on the suppressed channel. Suppression sources: 1. Hard bounce → email bounced, address invalid → auto-suppress 2. Spam complaint → user marked as spam → auto-suppress 3. Admin action → admin manually suppresses a user 4. GDPR deletion request → user requests data deletion → suppress all channels 5. Carrier block (SMS) → carrier rejected messages → auto-suppress number Check: EMAIL: gdpr.email_preferences WHERE user_id = :uid AND suppressed_at IS NOT NULL SMS: marketing.user_communication_preferences WHERE user_id = :uid AND channel = 'sms' AND suppressed_at IS NOT NULL WA: marketing.user_communication_preferences WHERE user_id = :uid AND channel = 'whatsapp' AND suppressed_at IS NOT NULL Suppression also syncs to provider: → email_provider.sync_suppression(suppressed_emails) → Prevents provider from even attempting delivery

Guardrail 3: Frequency Cap

FREQUENCY CAP: Per-User Message Limits ▼
Frequency cap prevents over-messaging users. Configured per channel in messaging_config. Configuration (admin-editable via API): { "frequency_caps": { "email": { "marketing": { "max_per_window": 3, "window_days": 7 }, "transactional": null // no cap on transactional }, "sms": { "marketing": { "max_per_window": 1, "window_days": 7 }, "transactional": { "max_per_window": 3, "window_days": 1 } }, "whatsapp": { "marketing": { "max_per_window": 2, "window_days": 7 }, "transactional": null } } } Check: SELECT COUNT(*) FROM marketing.message_pressure_log WHERE user_id = :uid AND channel = :channel AND message_type = :message_type AND sent_at >= NOW() - INTERVAL ':window_days days' If count >= max_per_window → SKIP (reason: "frequency_cap") Tracking: Every successful send inserts into message_pressure_log: INSERT INTO marketing.message_pressure_log ( user_id, channel, message_type, campaign_id, flow_id, sent_at ) This table is the source of truth for frequency cap enforcement. It's lightweight (no content, just counts) and indexed on (user_id, channel, sent_at). Priority override: If a campaign is marked "high_priority" and user has 1 slot left in their cap, the high-priority campaign takes the slot and lower-priority campaigns are blocked.

QUIET HOURS: Time-of-Day Gating ▼
Quiet hours prevent messages from arriving at inappropriate times. Guardrail 5: Sunset Policy

SUNSET: Auto-Stop Sending to Unengaged Users ▼
Sunset policy automatically stops messaging users who haven't engaged. This protects sender reputation and reduces cost. Configuration: { "sunset_policy": { "enabled": true, "email": { "inactivity_days": 90, // no opens/clicks in 90 days "action": "suppress_marketing" // suppress_marketing | suppress_all | tag_only }, "sms": { "inactivity_days": 60, "action": "suppress_marketing" }, "whatsapp": { "inactivity_days": 60, "action": "suppress_marketing" } } } Daily Sunset Worker checks: FOR EACH channel: SELECT u.id, u.email FROM core.users u WHERE u.id NOT IN ( -- Users who engaged (opened/clicked) within the window SELECT DISTINCT cr.user_id FROM marketing.campaign_recipients cr WHERE cr.channel = :channel AND (cr.opened_at IS NOT NULL OR cr.clicked_at IS NOT NULL) AND cr.created_at >= NOW() - INTERVAL ':inactivity_days days' ) AND u.id IN ( -- Users we've actually sent to (don't sunset users who never received anything) SELECT DISTINCT cr.user_id FROM marketing.campaign_recipients cr WHERE cr.channel = :channel AND cr.sent_at IS NOT NULL ) For each unengaged user: IF action = "suppress_marketing": → Update preferences: marketing consent = false for this channel → User still receives transactional messages IF action = "suppress_all": → Full suppression on this channel IF action = "tag_only": → Add tag "sunset_candidate" (admin reviews before action) Engagement score integration: Users with engagement_score > threshold are NEVER sunset (they might be engaging via a different channel)

Guardrail 6: Fatigue Detection

FATIGUE: Dynamic Engagement-Based Throttling ▼
Fatigue detection goes beyond simple frequency caps. It detects declining engagement TRENDS and throttles proactively. Signals: 1. Declining open rate: user opened 5 of last 10 emails → 2 of last 10 → trending down 2. No clicks in N messages: received 5 emails, clicked 0 → fatigue 3. Engagement score velocity negative: score dropping over time 4. Unsubscribe signal: user visited unsubscribe page but didn't complete Algorithm: fatigue_score = ( 0.4 × (1 - recent_open_rate) + 0.3 × (1 - recent_click_rate) + 0.2 × max(0, -engagement_velocity / 10) + 0.1 × (recent_unsubscribe_page_visits > 0 ? 1 : 0) ) If fatigue_score > 0.7 → SKIP (reason: "fatigue") If fatigue_score > 0.5 → reduce frequency cap by 50% If fatigue_score < 0.3 → normal sending This is a softer gate than sunset — it doesn't permanently suppress, it just temporarily reduces message frequency until engagement recovers. Dashboard alert: Admin sees: "47 users showing fatigue signals in the last 7 days" with breakdown by channel and recommended action.

Guardrails in the Delivery Pipeline: Where They Run

Guardrail When Checked Outcome if Failed Applies To
Consent Before any send SKIP (immediate, permanent for this send) All channels, all message types
Suppression Before any send SKIP (until suppression lifted) All channels, overrides consent
Frequency cap Before each send SKIP (until window expires) Marketing only (configurable per channel)
Quiet hours Before each send DEFER (reschedule for morning) Marketing only (transactional bypasses)
Sunset Daily background check SUPPRESS channel (long-term) Marketing only, per channel
Fatigue Before each send SKIP or reduce frequency Marketing only
Transactional Messages Bypass Most Guardrails

Password resets, email verification, order confirmations, and security alerts skip frequency caps, quiet hours, sunset, and fatigue checks. They only respect suppression (hard block) and transactional consent (which defaults to true for all users).

This is controlled by the message_type field on the DeliveryRequest. If message_type = "transactional", the guardrails pipeline short-circuits after consent + suppression checks.
