Stage 1: Audience Discovery

YOUR APP ADMIN ACTION

The admin identifies WHO to target. This is the entry point to the entire pipeline. Entirely in your app — Brevo is not involved.

User Stories (9)

US-1.1 As an admin, I want to write a custom SQL query that returns user_ids so that I can target a specific behavioral segment.
US-1.2 As an admin, I want to toggle a saved metric as "audience-eligible" so that it appears in the Campaign Wizard audience picker.
US-1.3 As an admin, I want to use a preset segment (Champions, At-Risk, Cart Abandoners, etc.) so that I can quickly target common audiences without writing SQL.
US-1.4 As an admin, I want to combine multiple audiences (metric A AND segment B) so that I can create intersected targeting.
US-1.5 As an admin, I want to preview the audience size before creating a campaign so that I know how many users I'm targeting.
US-1.6 As an admin, I want to exclude users who are already in another active campaign so that I don't over-message them.
US-1.7 As an admin, I want to save an audience query for reuse across multiple campaigns so that I don't have to rebuild it each time.
US-1.8 As an admin, I want to create an audience from campaign engagement results (e.g., "users who opened Campaign A but didn't click", "users who clicked but didn't purchase") so that I can re-target based on past campaign behavior.
US-1.9 As an admin, I want to target users who appear in multiple campaign audiences (e.g., "received Campaign A AND Campaign B but converted on neither") so that I can identify resistant segments and try a different approach.
admin has at least one saved metric with is_audience=true OR one audience segment → audience picker shows options
custom metric SQL returns a user_id column → system validates and accepts as audience
audience query returns 0 users → warn admin, block campaign creation
Tables: analytics.saved_metrics, marketing.audience_segments, marketing.audience_group_presets. New segment filter types: campaign_engagement (opened/clicked/converted by campaign_id), multi_campaign_overlap (in campaign A AND B), engagement_score (threshold, velocity). These extend marketing.audience_segments filter schema.

Stage 2: Campaign Creation

YOUR APP ADMIN ACTION

The admin designs the campaign — choosing medium, content, tracking settings, and optional A/B testing. Entirely in your app — stored in your DB. Brevo is not involved until send.

User Stories (9)

US-2.1 As an admin, I want to choose a medium (Email, SMS, WhatsApp) so that I can reach users on their preferred channel.
US-2.2 As an admin, I want to design email content with a visual template editor so that I can create professional-looking campaigns without coding.
US-2.3 As an admin, I want to create A/B variants with different subjects so that I can test which subject line performs better.
US-2.4 As an admin, I want to set a custom attribution window (e.g., 7 days, 14 days, 30 days) so that I can control how long post-campaign user activity is tracked.
US-2.5 As an admin, I want to enable click heatmap tracking for this campaign's emails so that I can see where users click most within the email layout.
US-2.6 As an admin, I want to add UTM parameters automatically based on campaign name so that on-site visits are attributed to this campaign.
US-2.7 As an admin, I want to schedule a campaign for a future date/time so that I can plan ahead.
US-2.8 As an admin, I want to send a test to myself before launching so that I can preview how it looks.
US-2.9 As an admin, I want to set campaign-level goals (target conversion rate, target revenue) so that I can measure success against expectations.
medium = SMS → content limited to 160 chars (or concatenated), no heatmap
medium = WhatsApp → must use Brevo-approved template for first message
medium = Email → heatmap tracking available, A/B variants available
A/B testing → min 2 variants, split rule percentage, winner criteria (open or click), test duration
audience has no phone numbers → SMS/WhatsApp medium disabled with warning
Tables: marketing.campaigns, marketing.campaign_variants, marketing.campaign_segments. New fields: attribution_window_days, enable_heatmap, goal_conversion_rate, goal_revenue

Stage 3: Delivery

YOUR APP + BREVO SYSTEM ACTION

System resolves audience, syncs contacts to Brevo, sends messages, and logs every recipient. Your app resolves the audience, syncs contacts, and logs recipients. Brevo handles the actual email/SMS/WhatsApp delivery and fires delivery webhooks back to your app.

User Stories (5)

US-3.1 As a system, I must resolve the audience query to a list of user_ids with their contact info (email, phone) so that I know who to send to.
US-3.2 As a system, I must sync resolved contacts to Brevo's contact database so that Brevo campaign sends can reach them.
US-3.3 As a system, I must record every recipient in a campaign_recipients table so that we can track per-user campaign delivery.
US-3.4 As a system, I must rewrite all links in email content to include campaign tracking parameters so that click-through visits are attributed.
US-3.5 As an admin, I want to see real-time delivery progress (sent/delivered/bounced counts) so that I know the campaign is running.
user is_verified=false → skip (unless overridden)
user marketing_email=false → skip for email medium
user suppressed_at IS NOT NULL → skip
user has no phone number → skip for SMS/WhatsApp medium
Brevo returns bounce → mark recipient as bounced, update suppression list
INSERT-BEFORE-SEND (F20): INSERT campaign_recipients row with status='sending' BEFORE calling Brevo API. If Brevo returns success → update to 'sent'. If Brevo returns error → update to 'failed'. This prevents lost tracking if webhook arrives before the send callback returns (race condition). Never fire-and-forget the send without a pre-existing recipient row.
NEW table: marketing.campaign_recipients (campaign_id, variant_label, user_id, email, phone, medium, provider_message_id, status [sending/sent/delivered/bounced/failed], sent_at, delivered_at, opened_at, clicked_at). Status lifecycle: sending → sent → delivered (or bounced/failed at any point).

Stage 4: In-Message Interaction Tracking

BREVO → YOUR APP USER ACTION + SYSTEM TRACKING

User interacts with the campaign message. Brevo tracks opens, clicks, and proxy opens automatically and fires webhooks. Your app receives those webhooks and stores them for heatmap/analytics. The user never touches your app at this stage — they're in their email client, phone, or WhatsApp.

User Stories (10)

US-4.1 As a system, I must record when a user opens an email (webhook: opened) so that open rates are tracked.
US-4.2 As a system, I must record which specific link a user clicks (webhook: click + URL) so that we know what content drives action.
THREE-LAYER HEATMAP SYSTEM

Email clients strip all JavaScript — no mouse tracking inside emails is possible. We use three complementary layers to get full heatmap coverage of campaign content.

US-4.3a LAYER 1: INVISIBLE LINK GRID
As an admin, I want the email template builder to automatically slice every visual section of the email into distinct clickable zones (hero-left, hero-center, hero-right, product-1-image, product-1-title, product-1-price, product-1-button, footer-social, etc.) — each zone is a unique tracked URL going to the same destination but with a different position ID. This gives me a heatmap OF the email itself showing exactly which zones users click, not just which CTA buttons.
HOW: At send time, the system rewrites the email HTML to wrap every section in a tracked link with a unique pos=zone-id param. Brevo click webhooks return the URL including the zone param. We store zone clicks in campaign_link_clicks. Admin sees an overlay of the email template with zones color-coded by click frequency. Coverage: 100% of clickers. Granularity: 20-100 zones per email.
US-4.3b LAYER 2: MIRROR PAGE
As an admin, I want every email to include a "View in browser" link that opens a mirror page on our website rendering the exact same email content — but with full JS heatmap tracking (mouse coordinates, scroll depth, hover time, click positions). This gives me pixel-level heatmap data of the email content itself from the ~5-15% of users who click "View in browser."
HOW: Mirror page at /campaigns/{slug}/mirror?uid=X&cid=Y renders the email HTML + loads our click tracker JS + Clarity. Full mouse/click/scroll recording. Data stored in page_click_interactions. Coverage: 5-15% of recipients. Granularity: pixel-level.
US-4.3c LAYER 3: CAMPAIGN LANDING PAGE
As an admin, I want the campaign email to drive users to a dedicated campaign landing page on our site where the full campaign content lives (product showcases, forms, interactive elements). This page has full JS heatmap tracking + Clarity. The email is the teaser, the landing page IS the campaign. I get full heatmaps on the actual campaign experience.
HOW: Landing page at /campaigns/{slug} with our click tracker JS + Clarity. All interactions attributed to campaign via UTM. Data stored in page_click_interactions. Coverage: everyone who clicks through. Granularity: pixel-level.
US-4.3d As an admin, I want to aggregate heatmap data across multiple campaigns (e.g., 5 campaigns) so that I can see patterns in where users consistently click and optimize my templates and pages accordingly.
Layer 1: aggregate zone clicks by position_id across campaigns sharing the same email template. Layer 2: aggregate mirror page click coordinates across campaigns. Layer 3: aggregate landing page click coordinates across campaigns driving to the same page template. All three layers are aggregatable independently or combined.
US-4.4 As a system, I must record time-to-open (gap between delivery and first open) so that we know when users are most responsive.
US-4.5 As a system, I must distinguish bot clicks from human clicks (clicks <2 seconds after delivery are likely bots) so that engagement metrics are accurate.
US-4.6 As a system, I must detect Apple MPP proxy opens and flag them separately so that open rates reflect real engagement.
US-4.7 As an admin, I want to see per-link click counts for SMS/WhatsApp campaigns so that I can evaluate CTA effectiveness across all mediums.
event = proxy_open or unique_proxy_open → flag as "proxy" in our DB, show separately in stats
time-to-click < 2 seconds → flag as probable bot click
medium = SMS → no open tracking (SMS doesn't support it), only click tracking via short URLs
medium = WhatsApp → delivery + read receipts from Brevo, click tracking via links
WEBHOOK RECONCILIATION (F10): A scheduled job runs every 6 hours and pulls Brevo campaign stats via GET /emailCampaigns/{id}/statistics. It compares Brevo's aggregate counts (sent, delivered, opened, clicked, bounced, unsubscribed) against our campaign_recipients aggregate. Any missing events are backfilled. This catches webhooks lost to network issues, app downtime, or Brevo retry exhaustion. A "last reconciled at" timestamp is shown on the campaign dashboard.
Expand gdpr.email_webhook_events to store: opened events (with user_agent, device), click events (with URL, user_agent, device, is_bot flag, is_proxy flag). NEW table or columns: marketing.campaign_link_clicks (campaign_id, variant_label, user_id, link_url, link_position, clicked_at, is_bot). Reconciliation metadata stored in marketing.campaigns: last_reconciled_at, reconciliation_delta (JSON — counts diff at last reconciliation).

Stage 5: Website Attribution

YOUR APP SYSTEM TRACKING

User clicks through from campaign to website. Your app detects UTM params, links the session to a campaign, stores a first-party cookie, and starts the attribution window. Brevo is not involved — this is your tracking middleware.

User Stories (5)

US-5.1 As a system, I must detect UTM parameters on landing and resolve them to a campaign_id so that the visit is attributed to the right campaign.
US-5.2 As a system, I must store the campaign_id in a first-party cookie with the configured TTL (attribution window days) so that return visits within the window are still attributed.
US-5.3 As a system, I must link the current session to the campaign in our DB so that all page views and events in this session are campaign-attributed.
US-5.4 As a system, I must continue attributing user sessions to the campaign for X days (configurable per campaign) so that delayed conversions are tracked.
US-5.5 As a system, I must handle multiple campaign attributions (user clicked campaign A on Monday, campaign B on Wednesday) by storing all touchpoints for multi-touch attribution.
user is authenticated → use server-side user_id for reliable attribution
user is anonymous → rely on first-party cookie for session linking
attribution window expired → no more campaign credit for this user's actions
user has multiple campaign cookies → store ALL touchpoints (multi-touch)
no UTM params but user came from campaign link → fallback to referrer detection
NEW table: marketing.campaign_attributions (id, user_id, session_id, campaign_id, variant_label, medium, touchpoint_type [click/open/visit], touchpoint_at, attribution_window_end). Modify analytics.utm_tracking to add campaign_id FK.

Stage 6: On-Site Engagement Tracking

YOUR APP USER ACTION + SYSTEM TRACKING

User browses the site. Your app tracks every interaction (page views, product views, cart adds, purchases) and links them to the originating campaign(s). Entirely your tracking module — Brevo is not involved.

User Stories (6)

US-6.1 As a system, I must track all page views with path, duration, and scroll depth during attributed sessions so that post-campaign engagement is measured.
US-6.2 As a system, I must fire and store product_viewed events so that we know which products attracted campaign-driven visitors.
US-6.3 As a system, I must fire and store add_to_cart events so that we track purchase intent from campaigns.
US-6.4 As a system, I must fire and store checkout_abandoned events so that drop-off points are identified.
US-6.5 As a system, I must track click interactions on the website (which elements users click) so that we can build on-site heatmaps showing where campaign-driven users interact most.
US-6.6 As an admin, I want to adjust the attribution window per user (e.g., extend it for high-value prospects) so that I can customize tracking for important leads.
session has campaign attribution → all events in session tagged with campaign_id(s)
user returns within attribution window → new session still attributed
user returns AFTER attribution window → session NOT attributed to campaign
user converts (purchase) → mark campaign_recipients.converted_at, log revenue
Fire new events: product_viewed, add_to_cart, checkout_abandoned, purchase_completed. Add campaign_id to analytics.events for attributed sessions. NEW: on-site click tracking (element, coordinates, page) for heatmap.

Stage 7: Campaign-Level Analytics (Conversion Funnel)

YOUR APP (primary) + BREVO (supplemental) ADMIN VIEW

The campaign dashboard. Your app builds all funnel views from your own DB (campaign_recipients + webhook events + page_views + orders). Brevo provides supplemental per-campaign stats (globalStats, linksStats, statsByDevice) that you can pull periodically to enrich your dashboard. Cross-campaign aggregation, segment comparison, and attribution are 100% your app.

User Stories (8)

US-7.1 As an admin, I want to see the full conversion funnel for a campaign (Sent → Delivered → Opened → Clicked → Visited → Engaged → Added to Cart → Purchased → Revenue) with counts and drop-off rates at each stage.
US-7.2 As an admin, I want to see an email click heatmap showing which links and sections of the email got the most clicks, so that I can design future emails to match user behavior.
US-7.3 As an admin, I want to compare A/B variant performance side by side (open rate, click rate, conversion rate, revenue) so that I can pick the winning variant.
US-7.4 As an admin, I want to see performance broken down by audience segment so that I know which segments responded best.
US-7.5 As an admin, I want to see device/browser/email-client breakdown so that I know how users are consuming my campaigns.
US-7.6 As an admin, I want to see the time distribution of opens and clicks (heatmap by hour of day) so that I can optimize send times.
US-7.7 As an admin, I want to see revenue attributed to this campaign (total, per user, average basket) so that I can measure ROI.
US-7.8 As an admin, I want to compare this campaign's performance against campaign goals I set so that I can evaluate success/failure objectively.
campaign is still within attribution window → stats are "live" (still accumulating)
campaign attribution window closed → stats are "final"
A/B test → show winner badge, statistical significance indicator
PRE-AGGREGATION STRATEGY (F24): Campaign analytics are NOT computed on-the-fly for every page load. A marketing.campaign_stats_summary materialized table is refreshed periodically (every 30 minutes via background job) and on-demand (admin clicks "Refresh" button). This avoids the 6-table JOIN (campaign_recipients → webhooks → attributions → page_views → events → orders) on every dashboard view. The summary stores: sent, delivered, opened, clicked, visited, engaged, carted, converted, revenue, bounce_rate, open_rate, click_rate — per campaign + per variant.
Funnel query joins: campaign_recipients → email_webhook_events → campaign_attributions → page_views → analytics.events → ecommerce.orders. Pre-aggregated into marketing.campaign_stats_summary (refreshed every 30min + on-demand). Raw tables still used for drill-down views (per-user, per-link, time-distribution). NEW table: marketing.campaign_stats_summary (campaign_id, variant_label, sent, delivered, opened, unique_opened, clicked, unique_clicked, visited, engaged, carted, converted, revenue, last_refreshed_at).

Stage 8: User-Level Timeline

YOUR APP ADMIN VIEW

The user journey view — a chronological event stream for a single user across ALL campaigns and interactions. 100% your app. Brevo's per-contact stats (GET /contacts/{id}/campaignStats) is limited to 90-day windows and doesn't include on-site behavior. Your DB has everything needed.

User Stories (5)

US-8.1 As an admin, I want to see a chronological timeline of everything a user did — campaign deliveries, opens, clicks, site visits, page views, cart actions, purchases — so that I understand their full journey.
US-8.2 As an admin, I want to see campaign touchpoints highlighted on the timeline (which campaigns touched this user, when, and what happened after each) so that I can see which campaigns influenced their behavior.
US-8.3 As an admin, I want to see the user's engagement score over time (graph showing momentum rising and falling) so that I can understand their engagement pattern.
US-8.4 As an admin, I want to see which campaigns this user belongs to (active, completed, pending) and their status in each so that I know their current marketing context.
US-8.5 As an admin, I want to see the user's conversion history — what they purchased, when, and which campaign(s) are attributed — so that I can measure lifetime campaign impact.
Timeline query: UNION ALL across campaign_recipients, email_webhook_events, campaign_attributions, page_views, analytics.events, ecommerce.orders — all for one user_id, sorted by timestamp. Engagement score computed from weighted sum of recent events with decay.

Stage 9: Effectiveness Evaluation & Continuous Improvement

YOUR APP (primary) + BREVO (revenue data) ADMIN VIEW

The big picture. Your app computes all cross-campaign comparisons, multi-touch attribution, trend lines, and cohort analysis from your DB. Brevo can supplement with its own revenue attribution (GET /ecommerce/attribution/metrics) as a cross-check — but Brevo's model is fixed (last-click, 48hr) while yours is configurable. Insights from this stage feed back into Stage 1 — admin creates new audiences using campaign engagement filters based on what they learn here.

User Stories (4 + sub-views)

US-9.1 As an admin, I want to see a cross-campaign comparison dashboard showing all campaigns ranked by: conversion rate, revenue, ROI, engagement rate — so that I can identify what works.
US-9.2 As an admin, I want to see multi-touch attribution showing how combinations of campaigns contributed to conversions (e.g., "users who received campaigns A, B, and C converted at 3x the rate of those who received only A") so that I understand campaign synergy.
US-9.3 As an admin, I want to see time-based trend lines (weekly/monthly engagement rates, conversion rates, revenue per campaign) so that I can detect list fatigue, seasonality, and improvement over time.
US-9.4 As an admin, I want to switch between attribution models (last-click, first-touch, linear, time-decay, U-shaped) and see how the numbers change so that I can choose the model that best represents my business.

Stage 10: Automation Flow Builder

YOUR APP ADMIN ACTION

The admin builds automated multi-step sequences that fire when events occur. This is the "Klaviyo Flows" equivalent. 100% your app — flow definitions are stored in your DB, version-controlled, and template-portable. Brevo is only involved when a Send step executes (it goes through the same Stage 3 delivery pipeline).

User Stories (12)

US-10.1 As an admin, I want to create an automation flow by choosing a trigger type and defining a sequence of steps so that campaigns fire automatically when events occur.
US-10.2 As an admin, I want to add a Send step that sends an email, SMS, or WhatsApp message using a chosen template so that the flow can reach users on the right channel.
US-10.3 As an admin, I want to add a Wait step with a configurable delay (hours, days, or "until next weekday at 10am") so that messages are spaced out naturally.
US-10.4 As an admin, I want to add a Branch (IF/ELSE) step that splits the flow based on user behavior (opened previous email? clicked? visited page? has attribute? score above N?) so that flows adapt to each user's actions.

Stage 11: Flow Execution Engine

YOUR APP (engine) + BREVO (delivery) SYSTEM ACTION

The runtime engine that executes flows. Your app manages the state machine — enrollment, step progression, wait resolution, branch evaluation, goal checking. When a Send step fires, it goes through the same Stage 3 delivery pipeline (resolve → Brevo API → webhook). A background worker checks every minute for wait steps that have expired and advances those enrollments.

User Stories (8)

US-11.1 As a system, I must enroll a user into a flow when the trigger condition is met and create an enrollment record tracking their position in the flow.
US-11.2 As a system, I must execute Send steps by routing through the Stage 3 delivery pipeline (resolve contact → send via Brevo → log recipient → receive webhooks) so that flow messages have identical tracking to one-off campaigns.
US-11.3 As a system, I must process Wait steps by recording the resume_at timestamp and a background worker must advance enrollments whose wait has expired (checked every 60 seconds).
US-11.4 As a system, I must evaluate Branch conditions by checking the user's state (opened email X? clicked? visited page? attribute value? score?) and route to the correct path.
US-11.5 As a system, I must check the flow's Goal condition after every step and exit the user from the flow (with status "goal_completed") if the goal is met.
US-11.6 As a system, I must check consent and suppression before every Send step — if the user has unsubscribed or been suppressed since enrollment, skip the send and log it.
US-11.7 As a system, I must respect the global frequency cap — if a user has already received N messages this week (across ALL flows + campaigns), delay or skip the send step and log it.
US-11.8 As a system, I must handle flow chaining — when a user exits a flow with a specific tag/status, check if any other flows have a "flow exit" trigger matching that tag and enroll them.
ENROLLMENT UNIQUENESS (F21): UNIQUE constraint on (flow_id, user_id) WHERE status='active'. Check-and-insert in a single transaction (INSERT ... ON CONFLICT DO NOTHING or SELECT FOR UPDATE + INSERT). This prevents duplicate enrollments when the same trigger fires twice in quick succession (e.g., webhook retry, double-click). If re_entry_policy allows re-entry, the existing enrollment must be in a terminal state (completed/timed_out/exited) before a new one is created.

Stage 13: Messaging Guardrails & List Hygiene

YOUR APP SYSTEM + ADMIN CONFIG

Safety rails that prevent over-messaging, protect deliverability, and keep audiences healthy. These apply globally across ALL campaigns and flows. 100% your app. These are the features that separate a professional marketing platform from a spam cannon.

User Stories (10)

US-13.1 As an admin, I want to set a global frequency cap (e.g., "no user receives more than 3 marketing emails per week" or "max 1 SMS per day") that applies across ALL campaigns and flows, so that I don't burn out my audience.
US-13.2 As an admin, I want to set quiet hours per channel (e.g., "no SMS or WhatsApp between 9pm and 8am in the user's timezone") so that I respect users' time and comply with regulations.
US-13.3 As an admin, I want to set a sunset policy (e.g., "auto-suppress users who haven't opened any email in 90 days") so that my list stays healthy and deliverability stays high.
US-13.4 As a system, I must detect engagement fatigue (declining open/click rates across consecutive campaigns to the same user) and alert the admin before deliverability degrades.
US-13.5 As an admin, I want to set per-flow priority levels (e.g., cart abandonment = high, newsletter = low) so that when the frequency cap is hit, lower-priority messages are deferred first.
US-13.6 As a system, I must use send time optimization — either Brevo's sendAtBestTime for campaigns, or our own model based on historical open-time data — so that messages arrive when users are most likely to engage.
US-13.7 As an admin, I want to see a "message pressure" dashboard showing how many messages each user segment is receiving per week and which users are approaching the frequency cap, so that I can spot over-messaging before it becomes a problem.
US-13.8 As an admin, I want to configure dynamic content blocks within email templates (e.g., show different product recommendations based on user's browsing history, or different copy based on engagement score tier) so that one template can personalize for different users.
US-13.9 As an admin, I want to see a deliverability health dashboard (bounce rate trend, spam complaint rate, domain reputation indicators) so that I can catch problems before ISPs start blocking my emails.
US-13.10 As a system, I must automatically exclude users who already converted (purchased the promoted product, completed the goal action) from follow-up campaigns and flow Send steps targeting the same goal, so that we don't send "buy now" messages to people who already bought.
frequency cap exceeded → message queued for next available window, not dropped
quiet hours active + message is SMS/WhatsApp → delay to next allowed hour
quiet hours active + message is email → send anyway (email is not intrusive)
sunset policy triggered → user moved to "sunset_suppressed" status, reversible by admin
bounce rate exceeds 5% on a campaign → alert admin, suggest list cleaning
spam complaint rate exceeds 0.1% → alert admin, pause campaign sends
